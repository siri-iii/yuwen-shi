## 2. 项目定位

### 2.1 核心目标

本项目不追求真实生产级玉器鉴定系统，而是完成一个**展示效果完整、操作流程顺畅、课程主题明确**的 AI 辅助玉器鉴赏原型系统。

系统面向普通学习者，解决以下学习问题：

| 学习困难 | 系统解决方式 |
|---|---|
| 看见玉器图片后不知道纹样类型 | 上传图片后给出可能纹样类别 |
| 不了解纹样背后的文化含义 | 通过知识库展示纹样寓意、器型关联和时代背景 |
| 学习资料零散，缺少结构化入口 | 提供纹样知识库和相似案例推荐 |
| 玉器鉴赏学习门槛较高 | 用 AI 讲解文本降低理解成本 |

### 2.2 项目边界

系统只做以下内容：

1. 玉器纹样的辅助识别
2. 纹样文化知识展示
3. 相似案例推荐
4. 学习型讲解文本生成
5. 可操作原型展示

系统不做以下内容：

1. 玉器真伪鉴定
2. 玉器年代精确断代
3. 玉石材质科学检测
4. 市场估价
5. 生产级图像识别模型训练

### 2.3 展示导向原则

本次期末作业以展示效果为最终目标，因此系统设计采用以下策略：

| 原则 | 具体做法 |
|---|---|
| 前端展示优先 | 首页、上传页、结果页、知识库页需要完整美观 |
| 后端适当简化 | 后端只保留必要接口，避免训练复杂模型 |
| 数据人工精选 | 纹样知识、案例图片、解释文本由人工整理，保证内容质量 |
| 识别结果稳定 | 准备固定演示图片，确保演示视频中识别结果稳定 |
| 结果表达谨慎 | 使用“可能识别为”“匹配度”等表述，避免伪装成权威鉴定 |
| 视频效果优先 | 页面动线、结果卡片、知识库浏览需要适合录屏展示 |

## 3. 系统总体设计

### 3.1 总体流程

用户操作流程如下：

```text
进入首页
  ↓
点击“开始识别”
  ↓
上传玉器图片或选择系统示例图片
  ↓
系统展示识别中状态
  ↓
返回可能纹样类别和匹配度
  ↓
展示纹样文化解释
  ↓
推荐相似玉器案例
  ↓
用户进入知识库继续浏览
```

### 3.2 系统架构

```text
┌──────────────────────────────┐
│            前端展示层          │
│ 首页 / 上传页 / 结果页 / 知识库 │
└───────────────┬──────────────┘
                │ HTTP 请求
                ↓
┌──────────────────────────────┐
│            简化后端层          │
│ 图片接收 / 识别逻辑 / 数据读取  │
└───────────────┬──────────────┘
                │
                ↓
┌──────────────────────────────┐
│             数据层             │
│ patterns.json / artifacts.json │
│ demo_images.json / 图片资源     │
└──────────────────────────────┘
```

### 3.3 技术栈建议

| 模块 | 推荐技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 或 React | 展示效果强，开发效率高 |
| UI | Element Plus / Ant Design / Tailwind CSS | 快速完成页面美化 |
| 后端 | Python Flask 或 FastAPI | 接口简单，适合课程展示 |
| 图像处理 | Pillow 或 OpenCV | 只做基础读取、缩放、相似度辅助 |
| 数据存储 | JSON 文件 | 减少数据库配置成本 |
| AI 讲解 | 模板生成或大模型接口预留 | 展示阶段可用模板生成，减少不稳定性 |
| 部署 | 本地运行 | 录制视频和现场展示更稳定 |

为了保证稳定性，建议使用**模板生成 + 知识库字段填充**，无需实时调用大模型。

模板示例：


填充后示例：

```text
系统识别该图片可能包含龙纹元素。从视觉特征看，该纹样通常表现为身体盘曲、线条流动、具有兽首结构。
```

2. 不依赖网络

## 5. 识别逻辑设计

## 5.1 总体策略

系统采用**演示型识别策略**：

```text
图片输入
  ↓
图片预处理
  ↓
与演示样本库进行匹配
  ↓
返回最接近纹样类别
  ↓
读取对应知识库
  ↓
生成结果页
```

### 设计原因

真实纹样分类模型需要大量标注图片，课程作业周期内成本较高。为了保证展示效果，本项目采用轻量匹配和人工知识库结合的方法，形成可演示闭环。

---

## 5.2 识别实现方案

### 推荐方案：示例图片映射 + 基础相似度匹配

#### 适用场景

适合作为课程展示版主方案。

#### 实现逻辑

1. 系统提前准备每类纹样的示例图片。
2. 后端为示例图片建立特征值。
3. 用户上传图片后，后端计算图片与样本库的相似度。
4. 返回相似度最高的纹样类别。
5. 如果图片来自示例库，系统稳定返回对应结果。
6. 如果图片不是示例库，系统返回相似度最高类别，并提示“仅供学习参考”。

#### 可选算法

| 算法 | 难度 | 展示效果 | 说明 |
|---|---|---|---|
| 文件名映射 | 低 | 稳定 | 示例图片直接返回对应纹样 |
| 感知哈希 pHash | 低 | 稳定 | 判断图片与样本是否相似 |
| 颜色直方图 | 低 | 一般 | 对玉器纹样识别帮助有限 |
| OpenCV 特征匹配 | 中 | 较好 | 可以展示技术感 |
| CLIP 向量检索 | 中 | 较好 | 需要额外依赖，展示效果强 |
| CNN 训练分类器 | 高 | 不稳定 | 数据量不够时不建议 |

### 最终建议

采用以下组合：

```text
示例图片映射
  +
pHash 或简单图像特征匹配
  +
人工知识库解释
```

这样可以减少后端复杂度，同时保证上传、识别、返回结果的演示过程完整。

## 7. 后端简化设计

## 7.1 后端目标

后端只承担三个任务：

1. 接收图片
2. 返回识别结果
3. 读取知识库和案例库

不做复杂后台管理、不做用户系统、不做模型训练、不做真实数据库管理。

## 7.2 后端接口

| 接口 | 方法 | 功能 |
|---|---|---|
| `/api/recognize` | POST | 上传图片并返回识别结果 |
| `/api/patterns` | GET | 获取全部纹样知识 |
| `/api/patterns/{pattern_id}` | GET | 获取单个纹样详情 |
| `/api/artifacts?pattern=dragon` | GET | 获取某类纹样的案例 |
| `/api/health` | GET | 检查后端是否运行 |

## 7.3 `/api/recognize` 处理逻辑

```text
接收图片
  ↓
保存到 uploads/
  ↓
判断是否为演示图片
  ↓
若命中演示图片映射，直接返回预设纹样
  ↓
若未命中，执行简单相似度匹配
  ↓
读取 patterns.json 中的纹样信息
  ↓
读取 artifacts.json 中的相似案例
  ↓
生成 AI 讲解文本
  ↓
返回 JSON 结果
```

## 7.4 后端代码文件建议

```text
backend/
├── app.py              # Flask 或 FastAPI 主入口
├── recognition.py      # 识别逻辑
├── knowledge.py        # 读取知识库
├── generator.py        # 讲解文本生成
├── config.py           # 路径配置
├── requirements.txt
└── uploads/
```

## 7.5 后端工作量控制

后端只需要保证演示闭环成立：

| 必须完成 | 可以省略 |
|---|---|
| 图片上传接口 | 用户登录 |
| JSON 数据读取 | 管理后台 |
| 返回识别结果 | 复杂数据库 |
| 返回案例数据 | 模型训练 |
| 返回讲解文本 | 云端部署 |
| README 运行说明 | 权限系统 |

## 14. 创新点表达

PPT 和说明文档中可以将创新点写为以下四点。

### 14.1 从静态学习到交互识别

传统玉器鉴赏多依赖教材图片和文字说明，本项目通过上传图片获得纹样识别结果，使学习者从被动阅读转向主动探索。

### 14.2 从图像结果到文化解释

系统不只输出纹样类别，还关联视觉特征、文化寓意、常见器物、历史时期和相似案例，形成从“识别”到“理解”的学习闭环。

### 14.3 基于知识库约束的 AI 讲解

系统的讲解文本基于人工整理的纹样知识库生成，减少生成式 AI 的不确定性，使解释内容更稳定、更适合课程展示。

### 14.4 软件工程方法服务玉文化传播

项目使用前后端架构、接口设计、数据建模、图像处理和可视化展示，将软件工程能力转化为玉文化传播工具。

## 15. 风险与应对方案

| 风险 | 表现 | 应对方案 |
|---|---|---|
| 识别准确率不足 | 随机图片识别结果不稳定 | 使用固定示例图片演示，结果表述为“可能识别为” |
| 后端开发时间不足 | 接口和模型来不及完成 | 采用 JSON 数据和示例图片映射，减少复杂逻辑 |
| 玉文化内容薄弱 | 系统像普通图像识别 Demo | 加强纹样知识库、文化解读和相似案例 |
| PPT 与系统脱节 | 讲得多，系统展示少 | PPT 使用真实页面截图，视频展示真实操作 |
| 图片来源问题 | 网络图片无出处 | 记录图片来源，优先使用公开博物馆和课程资料 |
| 视频录制失败 | 临时运行报错 | 提前录制视频，以视频作为最终展示保障 |
