## 各层职责说明

### 前端展示层
- 负责用户界面和交互体验，包含首页、上传识别页、结果页、知识库页、项目说明页共五个页面。
- 通过 HTTP 接口与后端通信：上传图片使用 `POST /api/recognize`，知识库浏览使用 `GET /api/patterns`。
- 识别结果、文化解读、相似案例均从后端 JSON 响应中读取并渲染，前端不直接访问数据文件。

### 简化后端层
- 使用 Python Flask 实现，只承担三项任务：接收图片、返回识别结果、读取知识库与案例库。
- 不含用户系统、管理后台、模型训练或云端部署，保证课程展示周期内可稳定运行。
- 跨域（CORS）已配置，前端本地开发时可直接调用。

### 数据层
- 使用 JSON 文件存储，不依赖数据库，降低环境配置成本。
- `patterns.json`：8 类纹样的视觉特征、文化寓意、常见器物、常见时期、鉴赏提示。
- `artifacts.json`：24 条玉器案例，每类纹样 3 条，含器物名、朝代、器型、图片路径、简介。
- `demo_images.json`：16 张示例图片与纹样类别的映射关系，保证演示结果稳定。

## 完整接口列表

| 接口路径 | 方法 | 功能 |
|---|---|---|
| `/api/health` | GET | 健康检查，确认后端正常运行 |
| `/api/patterns` | GET | 返回全部 8 类纹样知识 |
| `/api/patterns/<pattern_id>` | GET | 返回单类纹样详情 |
| `/api/artifacts?pattern=<id>` | GET | 返回指定纹样类别的玉器案例 |
| `/api/recognize` | POST | 上传图片，返回识别结果 + 文化解读 + 相似案例 + AI 讲解 |

## 识别逻辑说明

后端采用**展示型识别策略**，目的是保证演示视频中识别结果稳定、可预期：

**第一层：文件名映射（优先，结果 100% 稳定）**
- 上传文件名与 `demo_images.json` 中的键匹配时，直接返回预设的纹样类别和置信度。
- 演示视频录制时统一使用这些文件名上传，确保每次结果一致。

**第二层：pHash 相似度匹配（回退，适用于非示例图片）**
- 文件名未命中时，用感知哈希（pHash）算法将上传图片与样本库中的所有图片逐一比对。
- 返回汉明距离最小的纹样类别，并在结果中附加"仅供学习参考"提示。
- 该策略对光线、角度和图片质量有一定敏感性，结果仅作参考，不适合作为权威鉴定依据。

**为什么不训练真实分类模型？**
- 真实纹样分类模型需要大量标注图片，课程作业周期内收集成本较高。
- 本项目目标是展示系统完整性，不追求生产级识别精度，展示型策略可以保证演示效果。

---

## 系统局限性

- **数据规模**：仅覆盖 8 类常见玉器纹样，不能识别全部历史纹样类型。
- **识别精度**：非示例图片的 pHash 匹配对光线、拍摄角度、图片质量较敏感，结果仅供学习参考。
- **非专业鉴定**：本系统为学习辅助工具，不具备玉器真伪鉴定、玉石材质检测或年代精确断代能力。
- **部署范围**：目前仅支持本地运行，未做云端部署配置。
